# 离线计划的持久化边界

本文描述 schema 13 的存储保证；下载、组件预检和播放器调度由主进程协调器负责。

## 数据与上限

`LibraryStore` 在原有 SQLite 连接上管理四张表：`offline_plans`、`offline_plan_items`、`offline_media_refs` 和 `offline_job_owners`。多表操作使用同一个 `BEGIN IMMEDIATE` 事务，不另开离线数据库。

- 每个计划固定一本书、选择的稳定分集 ID 和引擎/设备配置，最多 1,000 集；最多同时保留 5 个未结束计划。
- 本地文件在创建时固定内容 hash；在线文件首次成功登记时固定 hash。后续下载不能悄悄换成另一个版本。
- `episodeOrder` 保留原分集排序值（本地从 0 开始，在线从 1 开始）；`ordinal` 是该计划内从 1 开始的顺序。
- renderer 的 `OfflinePlanItem` 不包含文件路径。内部 `StoredOfflineItem.file` 才保存媒体身份。
- 音频预算允许为 0。本地原文件不占在线保留预算；在线文件（包括已完整缓存的文件）按计划内不同的 `(path, contentHash, sizeBytes, modifiedAt)` 累计。因此 0 预算只适用于无需在线媒体保留的本地计划。重复登记或用新路径替换同一项的旧引用，不重复收取该项旧文件的额度。

## 控制修订与迟到响应

`plan.revision` 只随用户的暂停、恢复、取消、重试失败项、调整预算和解除保留增加。普通进度、统计和自动受阻不增加它，避免每个字幕分块都使界面按钮过期。

后台调度使用 `offlinePlanControl` 和 `offlineSchedulingPlans`，只查询计划 ID、控制修订、状态、配置与预算；后者仅返回最多 5 个 queued/running 计划。这些查询不扫描分集或字幕 coverage。界面统计仍由完整的计划查询计算，避免每遍历一集都重新统计整本书。

每次异步媒体或分集更新携带 `{planId, planRevision, itemId, attempt}`。提交时同一事务重新确认计划可运行、分集仍属于原书与原来源、控制修订与尝试号相同，且锁定的音频版本未变。暂停、取消、调整预算、重启恢复或自动受阻会废弃进行中的尝试；旧响应不能重新启用任务或登记文件。调整预算不会自动恢复受阻计划。

重扫删去分集或音频身份改变时，同控制修订/尝试号仍可仅写入失败或需处理原因，避免旧项永远停在处理中；这个例外不能写入时长、音频验证成功或新 hash，也不能越过暂停、取消或过期修订。

`blockOfflinePlan` 仅作用于同修订的运行中计划，保留已准备的内容和可恢复项。`retry-failed` 只重置失败/需处理项，不能恢复已取消计划，也不会自动复活用户取消的转写任务。

## 音频引用与失效

在线媒体登记、分集 hash 锁定、缓存所有权登记、预算复核和保留引用在同一事务提交。数据库故障会同时回滚这些操作；文件提交与失败清理由媒体协调器负责。

取消保留音频引用。只有终态计划可以显式解除保留；操作记录 `retentionReleasedAt` 并移除引用，不删除物理文件，也不影响另一计划对同一文件的引用。解除后，缓存管理器可以按通常规则处理已无保护的文件。

`invalidateOfflineMedia` 根据完整四元组将匹配项标为音频未验证，非取消项进入需处理状态，完成计划降为有问题完成。它增加相关项的尝试号，但不增加控制修订，不删除引用、不更换 hash、不自动下载。元数据检查由缓存扫描和协调器调用；真正使用前还需完整内容 hash 检查。仅凭持久化记录不能保证文件始终存在或没有静默损坏。

移除书籍会取消其未结束计划并增加控制修订，保留历史和音频引用，供用户以后显式解除保留；旧后台响应不能重新创建已移除的书。

## 字幕完成与任务归属

字幕成功必须满足当前音频身份、已验证媒体、正式文稿从 0 连续覆盖到实际音频时长，沿用字幕状态的 1 毫秒末尾容差。未知时长、内部覆盖缺口、仅有生成预览或 `job.status=completed` 都不能替代正式整集覆盖。检查只读取正式文稿的 coverage、kind 和 revision，不为计划列表读取整篇文字。

离线计划在进入已备状态或创建新转写任务前，先独立测量 Chromium 实际媒体时长；重启后尚未完成的项目会重新测量。`acceptJobSnapshot` 第六参数 `reportedDurationMs` 是 worker 的容器探测时长，可能包含编码填充，不等同于实际解码时长。数据库仅在时长尚为 NULL 时采用这个回退值，已有独立测量/播放时长保持不变，计划项同步数据库选定的时长；不会从 coverage 尾端反推。时长、生成稿和完成状态在同一事务写入，不调用 `saveProgress` 或改变播放位置。已有人工文稿继续受原来的自动采用保护，部分人工稿不会被后台完整预览覆盖。

`createOrAttachOfflineJob` 在同一事务创建/复用相同音频和引擎配置的活动任务，并关联计划项。任务归属区分：

- `planned`：曾属于计划，取消/暂停后仍保留此历史标记。
- `runnable`：至少一个可运行计划仍引用该任务。
- `manual`：原有手动任务或后来明确手动接管；在首次附着计划之前接管也会持久保存。

队列可以据此避免一个计划暂停时取消另一个计划或用户共享的任务。失败任务只在明确重试失败项后复用原任务；原 `cpuThreads` 和配置身份不会被当前资源偏好改写。用户取消的任务不会被计划自动重试。

## 验证

`tests/unit/offline-store.test.ts` 的 21 项真实 SQLite 测试覆盖 schema 12→13 迁移、1,000 集边界与分页、控制 CAS 与重启、零预算、精确引用与共享保留、事务故障回滚、完整覆盖/人工稿保护、持久任务归属、原线程配置重试、时长原子性、媒体失效、重扫删集、调整预算时的迟到响应、不读取资产/字幕的轻量调度查询、全项失效后的终态收敛，以及容器编码填充不能覆盖实际时长。最后一项保留在线实测的 52/40/31 毫秒差异，未放宽覆盖容差。

- `cache/optimization/offline-store-final.log`：18/18。
- `cache/optimization/offline-store-and-migrations.log`：当时的 14 项新增测试及受影响迁移/原文/字幕/缓存/队列，共 90/90。
- `cache/optimization/offline-store-queue-final.log`：18 项存储测试及 9 项真实队列测试，共 27/27。
- `cache/optimization/offline-scheduling-api.log`：20 项存储测试及 9 项真实队列测试，共 29/29。
- `cache/optimization/offline-duration-regression.log`：21 项存储测试、9 项计划队列测试及 22 项原队列测试，共 52/52；包括未知时长回退、失败回滚和已测时长保持。

这些测试不运行声学模型，不声称覆盖网络服务可用性、实际模型质量或所有操作系统存储故障；协调器和桌面验收的结果应另行记录。
