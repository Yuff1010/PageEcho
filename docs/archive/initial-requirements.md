# 听书软件功能总结与新软件需求草案

> 整理日期：2026-10-18  
> 用途：作为独立开发新听书软件的需求讨论与后续设计依据。  
> 状态：需求草案；已区分用户明确诉求、参考产品功能和建议方案。平台、技术栈、模型和开发排期尚未确定。

## 1. 项目目标

开发一款具有“随身听书”类似基础能力的听书软件，支持通过书源查找有声书、浏览目录、播放音频和管理收听进度，并重点解决“听书时缺少同步文字可看”的问题。

核心使用场景是：用户保留喜欢的有声书演播版本，在听音频的同时阅读与当前声音对应的文字；不需要因为有声书分集和小说章节不一致而反复寻找正文位置。

本文整理产品能力与独立实现需求，不预设复用随身听书源码、界面素材或现有插件代码，也不预设新软件兼容其插件格式。

## 4. 用户明确提出的问题

### 4.1 听书时没有可对照的文字

用户目前的收听体验中缺少同步文字。希望播放音频时能同时阅读，方便跟随内容和理解剧情。

这是用户当前使用中的问题，不等同于已经审计过随身听书所有版本均不提供任何文本能力。

### 4.2 有声书集数与原文章节不对应

用户给出的具体例子：

> 小说原文第19章的标题是“砍错”，但有声书中相关内容位于第32集，而且第32集开始时，已经是原文第19章的中间。

由此产生的需求约束：

- 不能使用“第32集对应第32章”的匹配方式。
- 仅比较章节标题，也无法确定集内位置。
- 一章原文可能被拆成多集，一集也可能跨越多章。
- 播放和阅读位置需要精确到集内时间与正文段落或句子。

### 4.3 希望探索 AI 转录伴读

用户提到起点小说中的 AI 语音转文稿体验，并询问能否采用类似方式：根据正在收听的音频生成可同步阅读的文字。

本文只把它作为用户期望的体验参考，没有确认起点内部的模型、实现流程或服务接口。

### 4.4 其他已知背景

- 用户希望新软件具备类似随身听书的基础听书能力，并可扩展搜书来源。
- 用户暂时没有指定需要接入的听书网站。
- 用户希望总结需求，以便自己重新开发软件；尚未确定开发平台、技术栈、模型或正式实施范围。

## 5. 新软件最重要的能力：音文同步伴读

### 5.1 区分两类文字

| 类型 | 来源 | 用户看到的内容 | 是否需要小说原文 |
|---|---|---|---|
| 音频转写稿 | 语音识别 | 演播音频实际说出的内容，可能有识别错误 | 不需要 |
| 小说原文 | 导入的正文 | 原作者写作的文本，可能与演播有删改差异 | 需要 |

界面应清楚标明当前显示哪一种，不能把 AI 转写稿直接标成“原文”。

### 5.2 建议优先验证的方案：音频转写伴读

流程：取得一集音频 → 检测人声并合理切段 → 语音识别 → 生成时间戳及标点 → 保存转写稿 → 跟随播放显示。

这一方案直接以第32集的音频为对象，不需要先找到小说第19章。对用户当前的“边听边看”诉求，依赖条件较少。

建议具备的体验：

- 展示当前集的转写稿，按句或短段落排版。
- 高亮当前正在播放的句子，并自动滚动。
- 用户拖动播放进度后，文字同步定位。
- 用户点击某句话，可以跳转到对应音频位置。
- 倍速播放、暂停和恢复后，仍按音频时间保持同步。
- 用户手动翻阅文字时暂时停止自动滚动，提供“回到当前播放位置”。
- 保存已完成的转写稿，重复收听时直接使用。
- 转写尚未完成或失败时，音频仍可正常播放，并显示可理解的状态。
- 支持修改识别错误，保留原有时间定位；大幅改动文本后可重新对齐。

### 5.3 转写任务与缓存

建议先测试预处理或提前分段处理，不把完全实时转写作为第一版前提。

- 优先处理用户当前选择的集与播放位置附近内容。
- 已处理的部分可先展示，剩余部分后台继续处理。
- 后续阶段可加入下一集预处理。
- 任务应能取消、重试并复用已完成片段，避免切书后继续消耗资源。
- 缓存绑定实际音频版本；同一集换了演播版本或剪辑内容后，不应复用错误的时间戳。
- 若切段识别，合并时保留在原音频中的时间偏移，处理分段边界的漏字或重复字。
- 若跳过片头或广告，仍保留原始音频时间坐标，避免整篇文稿发生偏移。

是否能边听边处理，取决于模型、设备和音频，需用实际样本测量。

### 5.4 转写质量问题

| 问题 | 建议处理方式 |
|---|---|
| 小说人名、地名、招式名称识别错误 | 支持专有名词表、人工纠错；有原文时辅助核对 |
| 音乐、音效、多人重叠说话 | 检测人声，对异常片段重试，并允许保留未识别标记 |
| 句子时间戳不准 | 增加时间对齐或人工微调能力 |
| 广告、片头、前情回顾混入正文 | 作为独立片段标注，可折叠；不随意删除导致时间错位 |
| 自动润色改变原意 | 默认只做标点、断句和有依据的纠错，不补写剧情 |
| 处理失败或资源不足 | 保留已完成内容，提示原因，并继续提供普通听书功能 |

## 6. 原文对齐及其他方案

以下为此前讨论过的备选或后续能力，不表示用户已决定全部实现。

| 方案 | 适用情况 | 主要取舍 |
|---|---|---|
| 手动定位与同步书签 | 用户有原文，愿意偶尔定位句子 | 实现相对直接；持续自动跟随仍需更多时间信息 |
| 已知原文与音频强制对齐 | 音频基本照读，且能确定对应文本范围 | 不必先完整转写；删改较多时容易错配 |
| 少量音频识别后检索原文 | 希望自动定位，同时减少转写量 | 需要原文及匹配机制，仍使用部分语音识别 |
| 完整转写后匹配原文 | 希望兼顾音频跟随和原文阅读 | 模块更多，需要处理删改、插话与不确定匹配 |
| 直接用原文 TTS 朗读 | 更重视正文同步，不要求保留现有演播 | 同步更容易，但声音不再是原来的有声书版本 |

原文对齐需支持“音频时间区间 ↔ 原文句子或段落”，不能把音频集与小说章固定绑定为一对一。匹配不确定时应允许用户确认，找不到对应内容时明确保留空缺。

## 7. 新软件的建议功能范围

下面是实施优先级建议，尚未由用户确认。

### 第一阶段：验证伴读核心体验

目标：用一集实际有声书，证明播放与转写文字可以稳定同步。

- 本地音频导入与基本播放。
- 转写处理、句级时间戳和缓存。
- 文稿显示、当前句高亮、点击跳转和拖动后定位。
- 播放与伴读位置恢复。
- 基本转写纠错、失败提示和任务重试。

先用本地文件验证，可以暂时排除网站失效、登录及音频地址过期等干扰；在线书源在下一阶段接入。

### 第二阶段：形成日常可用的听书软件

- 书架、最近播放、目录、断点续播、自动下一集。
- 倍速、定时停止、片头片尾设置、书签。
- 定义新软件的书源接口，接入选定网站，支持聚合搜索及按源筛选。
- 转录任务队列、当前集优先、下一集预处理与缓存管理。
- 字号、行距、主题、自动滚动开关等伴读设置。

### 第三阶段：增强与扩展

- 小说原文导入、跨集跨章匹配、手动校正同步点。
- 原文和转写稿切换、专有名词辅助纠错。
- 云同步、网盘、广播、多平台及更完整的插件管理。
- 转写稿或字幕导出、文稿搜索及文本书签。

## 8. 建议的模块划分

| 模块 | 责任 |
|---|---|
| 内容来源与书源适配 | 搜索、分类、书籍信息、目录与音频地址获取 |
| 媒体获取与缓存 | 处理音频请求、必要的会话与请求头、缓存和版本识别 |
| 播放器 | 播放控制、当前媒体时间、倍速、跳转及结束事件 |
| 转录任务服务 | 音频切段、模型或服务调用、任务状态、失败恢复 |
| 文稿与时间索引 | 保存句子文本、开始与结束时间、编辑内容和生成版本 |
| 伴读界面 | 高亮、滚动、点击句子跳转与用户阅读位置管理 |
| 书架与进度存储 | 书籍、当前集、播放位置、收藏、书签和设置 |
| 原文匹配服务（后续） | 导入正文、建立段落索引、匹配音频位置和记录人工校正 |

建议以播放器的媒体时间作为同步基准，不能按现实经过的秒数推算文字位置，否则倍速、暂停和跳转都会引起偏移。书源插件负责取得内容；转录和伴读应作为软件的公共能力，避免每个书源分别实现。

## 9. 核心验收场景

| 场景 | 预期结果 |
|---|---|
| 原文第19章对应有声书第32集，且从章中开始 | 转写伴读直接跟随第32集，不要求章节编号一致 |
| 一集音频跨越原文两章 | 转写不受影响；后续原文模式允许跨章映射 |
| 拖动到集内任意已转写位置 | 高亮和滚动定位到对应句子 |
| 倍速、暂停、恢复 | 文字继续按媒体时间同步，不累计漂移 |
| 点击一句转写文字 | 音频跳到该句对应位置 |
| 关闭后重新打开同一本书 | 恢复当前集、音频时间与相应伴读位置 |
| 文稿仍在生成或任务失败 | 普通播放保持可用，文稿状态明确，可重试 |
| 用户手动往上阅读 | 不被自动滚动反复拉回，可主动返回当前句 |
| 相同书名和集数换成另一个音频版本 | 不错误套用旧版本文稿时间轴 |
| 原文与演播存在插话或删改 | 原文模式不强行对应，允许空缺和人工确认 |

转写准确率、允许的同步误差、首段等待时间、内存占用和处理速度，需要先用代表性样本确定目标，不在本草案中承诺未经测试的数字。

## 10. 尚待确定的事项

- 第一版只做 Windows，还是需要跨平台？
- 是否主要保留真人演播音频？目前讨论按“保留现有音源”设计。
- 第一版仅显示转写稿，还是必须同时支持小说原文？
- 音频主要来自本地文件、在线书源，还是网盘？
- 是否有可导入的小说原文，格式是 TXT、EPUB 或其他？
- 转写使用本地模型、云端服务，还是两者可选？设备性能与预算是多少？
- 第一个适配的具体书源及用于测试的音频样本是什么？
- 是否需要兼容已有插件？这需要单独验证协议与运行时，不能默认可行。

以上问题用于后续选型，不影响先完成单集“音频＋同步转写稿”原型。
