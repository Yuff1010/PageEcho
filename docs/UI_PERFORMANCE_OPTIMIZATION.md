## 五项 UI 行为修复

### 1. 当前章节的按钮与播放状态一致

原章节行在正在播放时显示暂停图标，但点击总是调用 `player.load()`，会保存、清空媒体源并重新加载后播放。现在同一集已就绪时使用暂停／继续；不同集或需要重新加载时才执行加载。

当前行的图标、辅助名称及状态文字一并反映播放、暂停、正在加载或等待字幕。等待字幕时可取消等待，加载中的当前行暂时禁用，避免重复加载。

验证应检查：同集暂停／继续不触发新的 `loadstart`、媒体源不变、位置连续；切换另一集仍正常加载。核心回归还需覆盖字幕等待取消、加载失败重试、自然连播、跨集书签及点句跳转。

### 2. 移除有声书前明确说明数据影响

书架的“移除记录”先打开原生模态确认框，列出章节记录、收听进度、字幕及人工修改、书签、片段标注和相关任务记录会被删除，并说明不可撤销、原音频文件仍保留。默认焦点在“保留这本书”。

取消或按 Esc 关闭确认框时，不保存／停止播放器，也不发送删除请求；播放继续，用户资料保留。明确确认后才执行现有删除流程。若删除失败，错误留在确认框内供重试；确认后的失败仍可能已经停止该书播放，这是当前限制。

这项修复提供的是删除前确认。**书籍归档、隐藏后恢复、删除撤销及完整备份恢复尚未实现。** 独立电子书也使用同一确认框，准确说明书架记录／阅读位置会移除，重新导入后本书书签和单书设置可能无法恢复；仍供伴读使用的共享原文及原 TXT／EPUB 文件保留。电子书删除失败可在确认框内重试，取消／Esc 不调用删除接口。

验证在自有临时目录中进行：准备书籍、进度、人工字幕、书签和标注，分别取消、Esc、确认；前两者应保留资料与播放，确认后检查真实 SQLite 级联删除及原音频仍在。另需覆盖删除失败后的重试和焦点恢复。

电子书用例 `tests/desktop/ebook-removal-safety.spec.ts` 已在上述 dev.6 完整运行中通过：取消与 Esc 保留阅读进度和本机书签，并把焦点交还移除按钮；首次删除受控返回失败后，错误留在确认框，原记录仍在，随后重试执行真实删除。确认后检查 `reading_books` 已无记录，原 TXT 文件仍存在且 SHA-256 不变，焦点返回导入按钮。该错误为隔离应用的单次 IPC 回应注入，不冒充物理磁盘故障；也没有据此宣称删除了 localStorage 书签或验证了 EPUB 原文件的同等路径。

### 3. 电子书书架读取失败后可原位重试

首次书架读取失败后结束加载状态，显示错误及“重新加载书架”；不再同时永久显示“正在加载阅读书架”。成功读取前，导入保持禁用；重试成功后恢复可用。

每次页面显示／重试对应独立请求身份，离开页面后的迟到回应不会替换随后重新读取的书架。导入、移除等操作错误与读取错误分别处理。

桌面用例分别受控注入首次 Result 失败、Promise 拒绝和迟到交付；仅影响隔离应用的对应读取回应，后续请求仍经过原有受保护 IPC 和真实 SQLite。它们验证恢复流程，不等于真实设备或磁盘故障测试。重试后实际导入 TXT 并打开正文，防止只消除错误文字而功能仍不可用。

### 4. 播放进度支持实用的键盘定位

进度条获得焦点时，左右／上下方向键每次移动 5 秒，Home／End 定位到起点／终点，范围由播放器约束。辅助值使用“已播放时间，总时长”的可读表达。

内部值、鼠标定位、书签和点句仍保留原始音频毫秒精度；进度条的 `step=1` 没有改成粗时间单位。键盘处理取消对应默认行为，避免一次按键产生两次跳转。Alt／Ctrl／Meta 组合不由这段逻辑接管；本轮没有新增全局媒体键。

验证从 11,234 毫秒开始，单次方向键准确增减 5,000 毫秒，端点不越界；正常退出、重启后恢复 16,234 毫秒。此类数值是功能夹具的预期值，不是用户行为数据。

### 5. 字幕、书签入口直接定位目标区域

播放器“字幕与伴读”直接打开并聚焦“字幕与缓存”；书架／目录“本书设置与书签”直接定位“本书书签”。通用“收听工具”仍从“播放与定时”开始。对话框内保留原有分组导航。

`ListeningTools` 使用目标区域参数，打开后滚动并聚焦对应区域。关闭后回到原触发控件；来自弹出菜单的入口回到持续存在的菜单按钮，避免尝试聚焦已经卸载的菜单项。

确认框和收听工具均使用原生 `dialog.showModal()`。区域的 `tabIndex=-1` 用于程序聚焦，不额外增加常规 Tab 停靠点。已有自动化验证初始定位及关闭回退；视觉检查脚本另检查确认框 Tab／Shift+Tab 循环。Windows Narrator、系统高对比度和不同 DPI 仍需专门验证。

## 长文稿路径的实现

### 按文稿身份和修订条件读取

Main 增加 `getTranscriptIfChanged()`，按文稿 `id` 和 `revision` 在同一 SQL 查询中判断。修订未变时返回 `unchanged` 和版本，不读取、解析或传输整篇正文；首次、修订变化或调用方没有文稿时仍返回完整文稿。既有无条件 API 的返回形状继续保留。

Renderer 的 `TranscriptionStateClient` 为同一音频版本合并并发读取，并复用同修订的文稿对象。请求中收到新的变更通知会继续检查较新的版本；页面自身保留切集、卸载及迟到回应保护。缓存最多保留两份空闲完整文稿，活动请求完成后按容量清理。

预览按任务 `id`／`attempt`／`previewRevision` 重新读取，避免同一预览修订在进度通知中重复下载。正式稿和预览身份分开，用户草稿仍受原有修订保护。

### 播放器只读取所需的字幕状态

增加转写摘要接口，播放器读取任务小状态、文稿元数据及完整 coverage，不再为估算字幕领先范围读取所有句子。播放器同一时刻合并进行中的刷新，期间收到的新通知会触发后续读取。

coverage 保留全部离散区间，不用一个最大结束位置掩盖未覆盖空洞。目录、字幕等待与下一集逻辑仍遵循原音频时间及已有缓冲规则。

### 减少快照写入中的重复工作

真实任务快照仍进行完整合并与校验，并保留完整 JSON 写库。一次已校验文稿只编码一次；正式稿采用同一结果时复用编码，仅查询必要修订元数据。`INSERT … RETURNING` 返回写入后的身份与修订，避免为获取这些字段再次读取、解析整篇正文。

内部最多保留一个已提交任务快照，按任务、预览修订及 SQLite 外部 `data_version` 核对后复用。coverage 缓存最多 8 份，合计最多 100,000 个范围；对外返回时复制，避免调用方修改内部缓存。

缓存与事务须共同保持一致：读事务先建立真实 SQLite 读快照，再读取 `data_version`；写事务提交前不发布可能回滚的值，提交后携带该事务锁内核对的外部版本发布。正式稿写入清理相关缓存，外部连接提交使旧版本失效。

### 复用同一编辑事务内的读取

`TranscriptEditStore` 在单个同步 `BEGIN IMMEDIATE` 编辑事务内，按分集及音频版本复用已经读取的文稿，减少同一操作为校验、历史和结果准备而重复解析正文。任何写入前后都清空该事务的读取记录，写后结果重新读取实际存储内容；提交、回滚或异常退出时解除整份记录。

这份 read-through 记录不跨事务使用，也不复用到之后的名称替换预览或提交。既有 canonical／SHA-256 历史摘要、修订检查、实际写入及跨事务重新校验继续保留，没有用缓存命中替代用户修改保护。

这些是减少重复读取、解析和复制的优化，**没有实现增量文稿表、正文 delta 传输或新的存储 schema**。真正发生正文修订时，仍有随全文增长的校验、序列化、写入及编辑历史哈希成本。没有通过删减句子、截断 coverage、减少保护校验或只保留当前页来取得改善。

### 性能

最终比较已完成：同一台 Windows 机器，固定合成文本、静音 PCM、数据 SHA 和手动字幕配置，两个冻结版本串行运行。没有清空 OS 缓存或隔离其他用户进程，运行顺序固定为 before→after；数据库前后采集时间不同。这是本机小样本观测，不能外推为所有设备或用户的收益。

纠错采用同一 `fixed-target-small-ack-v2` 脚本、固定 `perf-0`，每种规模各 3 轮。单位毫秒，括号为最小—最大：

| 句数    | 改动前命令至 DOM 断言 | dev.6 命令至 DOM 断言 |
| ------- | --------------------- | --------------------- |
| 6,000   | 53.8（52.7–61.0）     | 52.4（50.7–55.4）     |
| 50,000  | 380.2（379.8–396.8）  | 356.0（346.5–356.5）  |
| 100,000 | 783.1（769.9–788.7）  | 679.8（674.5–687.9）  |

6,000 句的范围明显重叠，不宣称其纠错有确定提升。100,000 句的 30 条同修订通知压力段，中位完成时间由 4627.7（4574.5–4635.5）降至 3292.8（3289.9–3300.5）毫秒，各 3 轮；该时长包含目标 100 毫秒发送间隔，不能当作单次交互延迟。

真实 Store／SQLite 累计快照，每规模 3 个独立 Node 子进程，每进程 10 次固定大小追加，共 30 次。单位毫秒：

| 句数    | 改动前写入中位数 | dev.6 写入中位数 |
| ------- | ---------------- | ---------------- |
| 6,000   | 11.17            | 6.84             |
| 50,000  | 135.49           | 73.70            |
| 100,000 | 263.37           | 151.40           |

100,000 句写入范围由 259.34–295.46 变为 139.47–172.39 毫秒，P95 为 288.10→166.98 毫秒。该 Node／SQLite 子进程的观测 RSS 峰值约 810→838 MiB，**没有证明内存下降**；缓存减少重复解析，也保留额外对象。这不是整个 Electron／模型进程树的内存，更不是独占物理内存。

- 独立核对：[最终验证](../cache/optimization/ui-perf-dev6-final-validation.json)。它核对 155 个当前源文件、最终 8 个输出、12 个 Python 文件、原 `out/` 的 8 个文件、前后所有 renderer 样本的最终 SQLite 正文／修订／音频 SHA、Store 报告及测试／视觉证据；before／after 使用相同脚本与样本，原 `out/` 未变。

- 数据库脚本 `cache/optimization/long-transcript-baseline.ts` 测 6,000／50,000／100,000 句，每个规模 3 个独立子进程，每轮追加 10 次固定大小快照。它测真实 store／SQLite，同步调用耗时不等于 Electron 交互延迟。脚本要求当前源文件摘要与目标 manifest 一致；重测 before 须使用匹配的源副本，不能跳过校验。
- Electron 脚本 `cache/optimization/transcript-render-baseline.ts` 通过 `--app-root` 指向冻结应用，覆盖完整读取、打开正文、单句纠错及受控通知压力，记录 Main／renderer 指标和实际媒体时钟。每种规模先至少重复 3 轮并报告波动；重要交互应增加重复次数。
- 最终脚本口径为 `fixed-target-small-ack-v2`：在计时前固定选择 `perf-0`，避免播放推进使前后版本实际编辑不同句子。纠错与 JSON 导入的生产 IPC 仍完整返回到 renderer；仅从 renderer 回传给 Playwright Node 的测试回执缩为状态、改动数及修订，避免额外把整篇文稿再次传给测试端。操作前后仍另行核对全稿 SHA、句数、原媒体位置、暂停状态和倍速。
- 纠错计时从命令调用到 DOM 文本断言完成，不是物理点击到画面呈现；10Hz 同修订通知是压力条件，不宣称日常必然如此。媒体时钟推进也不能单独证明没有声音卡顿。

早期约 2.5 秒的观测包含额外的测试端全文传输，既不是物理点击延迟，也不能与小回执口径直接比较。早期原始报告保留，但不与最终新口径拼成前后收益；最终数值应来自同一固定目标、同一脚本口径的成对测量。

本轮结构性验收已通过：同修订通知不再反复携带全文、播放器摘要不含句子正文、真实修订完整显示并可搜索，事务、撤销、来源与人工保护保持。此前约 1.8 秒的候选目标基于旧工具口径，不作为正式门槛，也没有拿新口径宣称该目标达标。后续应在目标设备增加重复次数，再锁定正式延迟和资源预算；当前约 680 毫秒是特定夹具的基线，不是全设备 SLA。真实点击到呈现、冷启动、模型内存、长期稳定性及用户任务效率仍需相应范围的验证。
