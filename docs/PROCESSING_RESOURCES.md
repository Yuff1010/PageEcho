# 字幕处理资源控制

本文记录 0.15.0-dev.1 的线程控制、缓存边界和本机实测。Python 资源参数、真实模型及主进程暂停/恢复链路已通过验证；后台空闲切换另有真实 Electron/IPC 和受控 worker 验收。

## 使用

打开“缓存与任务 → 转写任务 → 处理资源”。低占用预设使用 1 个 CPU 数学线程及低进程优先级，也可选 1/2/4 线程、后台预取仅在电脑空闲满一分钟后处理。当前集手动生成优先，不更换书籍选择的引擎或设备。

“暂停处理”与播放器暂停独立，保留已完成分块并停止所属工作进程；未完成块可能需要重算。暂停跨重启保存，需明确恢复；已取消任务不会复活。无任务约 30 秒后回收闲置 worker，等待后台空闲时提前回收空闲进程。界面区分新任务配置、当前任务冻结配置与实际回报，模型未加载时实际线程保持未知。

数据库升级为 schema 12，保留已有书架、进度、稿件、人工原文和任务；旧任务线程补为 4。升级后的独立预览目录不能再由只支持旧 schema 的预览打开。

## 参数与实际生效范围

字幕 worker 和原文声学对齐脚本都接受 `--cpu-threads 1|2|4`，默认 `4`。线程数控制推理所使用的 CPU 并行度，不改变引擎、精度、模型版本、音频分块、时间戳算法或文本处理规则。

| 位置                      | 4 线程默认行为                         | 1 / 2 线程行为                           |
| ------------------------- | -------------------------------------- | ---------------------------------------- |
| ML 导入前环境             | OMP、MKL、OpenBLAS、NumExpr 预算设为 4 | 对应预算设为 1 / 2                       |
| Torch intra-op            | `torch.set_num_threads(4)`             | 使用所选线程数                           |
| Torch inter-op            | 保留既有运行时策略                     | 限制为 1                                 |
| FunASR ASR、VAD、标点     | `ncpu=4`                               | `ncpu=1/2`                               |
| WhisperX / faster-whisper | `cpu_threads=4`                        | `cpu_threads=1/2`                        |
| FFmpeg 音频解码           | 保留原命令，不增加线程参数             | 显式传入 `-threads` 和 `-filter_threads` |

`asr_resources.py` 在模型加载后、ASR 推理后和标点处理后读回 Torch 的实际线程数。若库把低线程设置改回 4，任务报错，不把“请求 1 线程”当作“实际已是 1 线程”。原文声学对齐在加载及对齐后同样读回。`executionResources` 是协议消息的顶层诊断字段，包含请求预算、实际 Torch intra-op / inter-op 及四个环境变量；模型未加载时实际值为 `null`。它不进入模型质量证据或语义配置。读回值是最近一次已验证状态，不是所有原生库线程的实时采样。

线程预算不等于进程总线程数。Python 协议读取线程、原生运行时、解码子进程仍可拥有其他线程，也不承诺系统 CPU 百分比上限、硬内存上限或 GPU 占用上限。低进程优先级由主进程设置，与上述线程数分开。CUDA 模式仍会执行 GPU 模型，CPU 线程数不会限制显存或 GPU 并行度。

## 新任务、旧任务和缓存

新任务创建时保存线程数，之后修改资源偏好只影响以后创建的任务。已排队、正在执行和重试的任务继续使用创建时保存的线程数；旧任务按 4 线程处理。恢复同一任务不会借此切换线程配置。

worker 原来已有 `configuration.threads`，本次只使用这个既有字段。省略参数或显式指定 4 时，语义配置与原默认配置完全相同，没有增加缓存字段；1 / 2 的该字段不同，因此拥有独立配置指纹和分块缓存。不能在不同线程配置间直接复用结果缓存，也不能放宽重试时的配置一致性检查。执行诊断、进程优先级、暂停状态均不加入语义配置。

分块仍使用整集的绝对位置和既有缓存键规则。保存完成的块可以在同一配置下复用，调整播放优先位置不会改变缓存身份。线程数不是准确率指标；这次单样本文稿恰好相同，不能推断所有输入都逐字、逐时间戳一致。

## 暂停、恢复和空闲释放

以下是已实现代码的行为，实际 Main 生命周期测量待补充：

- 全局暂停会持久化暂停状态，停止派发新任务、终止当前预检或模型租约，并把运行任务转回待处理且增加 attempt。旧 attempt 的迟到结果不能写回当前任务。
- worker 可以在块间检查取消，不能把正在原生库内部执行的推理冻结为可恢复的内存快照。主进程先请求取消，默认 3 秒宽限后仍未退出则终止所属进程树。当前尚未完成提交的块可能需要重做；已经原子保存的块仍可复用。
- 恢复会以保存的任务配置重新开始，验证音频和配置，再读取有效分块缓存。它不会重新识别已验证的缓存块，也不重新采用已经失效或被人工修订保护挡住的结果。关闭后的模型需重新加载。
- 仅后台空闲处理使用系统空闲至少 60 秒的条件，只约束后台任务；前台任务仍可调度。用户恢复活动时，当前后台任务按中断流程让出资源。
- 模型空闲时仍在 worker 中持有权重。队列默认在无任务使用约 30 秒后关闭闲置 worker；暂停或等待后台空闲时，队列在当前活动结束后也会发起关闭。关闭进程才释放它持有的模型内存与显存。以上阈值不是最大响应延迟承诺，仍有调度、取消及进程退出耗时。

减少线程不会卸载权重；当前推理批量已经是 1，也没有通过降低采样率、删减上下文或更换小模型来节省内存。实际 Windows 任务管理器显示的工作集、私有提交、系统缓存与进程退出后的系统可用内存含义不同，不能混用。

## 真实中文 CPU 测量

测量日期为 2026-10-23，使用本地只读组件 `release/asr-component-0.7.0-win-x64` 的 Paraformer CPU 模型。音频为 AISHELL-4 公开人工参考连续样本 `continuous-solo-first.wav` 的原媒体 `0–30000 ms`，完整文件长 97177 ms。它是会议人声样本，不是有声书质量验收。

音频 SHA-256：`0153ed14924506d1139bdb6695c0236734f4d3e5068f181f7b958cf765838868`。冻结清单 SHA-256：`83e892faf6b4c426ad4ddde0211451bdf5eacbb1eb62c9b94468215f2be10896`。

每种线程配置各启动一个新 worker，使用独立新缓存，先运行 4，再运行 1。只采样本次拥有的进程树，没有清空 OS 文件缓存，也没有关闭或隔离用户其他进程；墙钟时间和系统占用可能受其影响，表中 worker CPU 核秒仍只归属于本次拥有的 worker。运行顺序没有随机化。这是单样本实效验证，不能用于基准排名或推导通用速度、能耗、温度、准确率结论。2 线程通过参数贯穿单测，本轮没有额外真实模型性能测量。

| 指标                             |          4 线程 |          1 线程 |
| -------------------------------- | --------------: | --------------: |
| 实际 Torch intra-op / inter-op   |           4 / 8 |           1 / 1 |
| 四个环境预算                     |          均为 4 |          均为 1 |
| 提交至最终结果墙钟时间           |        19.046 s |        25.120 s |
| 进程启动至最终结果墙钟时间       |        19.256 s |        25.330 s |
| 提交至结果的 worker CPU 总时间   |        35.875 s |        25.000 s |
| `recognizing` 事件至结果墙钟时间 |         5.926 s |        12.987 s |
| 同阶段 worker CPU 总时间         |        20.219 s |        12.984 s |
| 采样进程树 RSS 峰值              | 7,171,080,192 B | 6,852,009,984 B |
| 采样 worker RSS 峰值             | 7,162,437,632 B | 6,843,367,424 B |
| 采样进程树私有提交峰值           | 9,774,747,648 B | 9,154,244,608 B |
| 采样 worker 总线程数峰值         |              20 |              10 |
| 完成后空闲 1 秒的 worker RSS     | 6,807,805,952 B | 6,791,811,072 B |
| 同 worker 同配置缓存重放         | 72 ms，命中 1/1 | 74 ms，命中 1/1 |

CPU 总时间是进程消耗的各核时间之和，可以大于墙钟时间。阶段名后的耗时包含该事件之后的对齐及后处理，不等于单独声学网络计时。RSS / 私有提交按约 100 ms 采样，可能遗漏尖峰或短命子进程；树 RSS 叠加也可能重复计算共享页。worker CPU 时间在阶段事件附近直接读取，树中短命子进程只统计被采到的部分。

1 线程在这次样本上减少了 CPU 总时间，并延长了等待时间；两种配置空闲时仍保留约 6.8 GB RSS，不能据此宣称低线程模式解决模型内存占用。

两个解码器均产生 480000 个 float32 样本，PCM SHA-256 相同：`df1e4f0cdd54adef3b581654b31acf36bd5c2702b26b450aab0f9224a4d42074`。两次最终文稿的文字、时间及 segment ID 完全相同；配置缓存键按预期不同。同配置缓存重放均命中 1/1，未出现解码、加载、识别阶段。这些是资源与缓存检验，不是人工准确率检验。

另外执行了一个已验证支持的 2.78 秒原文声学对齐 CPU 样本，`--cpu-threads 1` 后实际 Torch 为 1 / 1，四个环境预算均为 1；原结果协议正常并产生可预览结果。耗时 8883 ms，仅用于确认资源参数到达该脚本，不扩大声学质量实验的分母或结论。

## 主进程与实际播放验证

`cache/optimization/processing-resources-main-dev1-final-2026-10-23/report.json` 绑定同一最终预览、输出/Python 摘要、原音频、人工参考及组件清单，实际使用完整 97.177 秒 AISHELL-4 语音和 Paraformer CPU 1 线程：

1. 首个 30 秒分块完成，实际线程为 1、原生进程优先级低，启动静音真实媒体。
2. 暂停后同一 job 从 attempt 1 排回 attempt 2，稿件及首块保留，所属 worker 及子树实际退出。音频从约 9.5 ms 继续播放到 4037.5 ms。
3. 完整退出并重启，五次采样仍保持暂停、没有新 worker，文稿和缓存 JSON 摘要均不变。
4. 明确恢复同一任务/attempt/线程，首块缓存命中。回放缓存时实际线程为 null；之后未缓存推理明确读回 1。最终 4/4 块覆盖 0–97177 ms、cacheHit=1，播放器仍播放。
5. 两次关闭均为正常退出，所属进程树消失，rendererErrors 为空，受保护文件摘要未变；其他用户进程未操作。

首轮 runner 在缓存回放后过早断言线程已知而失败；原报告与日志保留，修正 runner 后独立完整重跑通过，没有修改产品来迎合该断言。墙钟不作性能基准，没有清 OS 缓存或隔离用户其他进程。

`resource-worker-desktop-final.log` 的 2 项资源流程使用受控 worker，实际验证 preload、IPC、SQLite、媒体时钟、原生优先级低→普通→低、暂停/重启/恢复/取消，以及 idle 0→120→0→120 秒时后台让出和恢复，另 5 项原文回归通过。`resource-ui-v1.log` 的 2 项资源 UI 与 8 项组件引导通过，包含脏稿/CAS 冲突、720×600 和播放不中断。

最终合计 227 项逻辑、12 项 Node、133 项 Python 和 44 个不同桌面检查通过。`cache/optimization/audit-resource-batch.py` 对最终源码、输出、Python、原 `out/`、CPU 实测和 Main 报告做只读核对，结果为 `resource-final-validation.json`。本批未宣称硬内存/GPU 限额或小说人工准确率。
