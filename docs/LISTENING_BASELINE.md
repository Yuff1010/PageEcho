## 输入与流程

用户指定的 CloudMusic 顶层有 12 个音频，ffprobe 确认容器与编码均为 FLAC。12 首分别通过实际播放、1.5 倍速、中点定位后继续播放；测试使用独立临时目录中的逐字节副本。结束后 12 个原文件的大小、修改时间及 SHA-256 与副本一致。

自然连播采用准备清单中的前三首，时长为 168.007、229.795、164.825 秒，合计 562.627 秒。全程 1 倍速、音量 0.05，没有推进测试时钟、伪造 ended 或在测量期间跳到末尾。第一曲同时启动新的 WhisperX CPU 任务，自然进入第二曲后启动 GPU 任务；第三曲不新建转写任务，设置“本集结束时停止”。两个任务分块缓存命中均为 0，分别完成 6/8 块。

模型在独立 v2 组件中运行，PATH 仅保留 Windows 系统目录，Chromium offline，worker 延续本地离线约束。应用使用新的用户数据/分块缓存，模型和 OS 文件缓存可能已预热，桌面其他负载未隔离；结果限于本机这次运行。

IPC 是 renderer→main→renderer 的小型状态读取；往返还包含测试调度，不是物理点击到画面延迟。媒体时钟和事件正常也不证明声音听感无杂音。RSS 汇总可能重复计算共享页，不等于独占物理内存；短周期采样可能漏掉瞬时峰值。口径依据见 [psutil API](https://psutil.io/api/)。

首轮 sampler 的 PID 是 Playwright 的 cmd.exe 启动器，其后代包含实际 Electron 和两个 Python worker。报告已澄清口径，原记录另存为 `report-before-scope-clarification.json`，数值未改。后续脚本改用主进程实际 PID；独立 `sampler-smoke.json` 验证根为 electron.exe、采样完成且原生窗口 hide/show 状态正确。

## 同时处理不等于从开头就有文稿

| 任务                      | 输入时长  | 观测首个前缀 | 观测任务结束 | 总耗时/音频时长 |
| ------------------------- | --------- | ------------ | ------------ | --------------- |
| WhisperX CPU int8         | 168.007 s | 约 27.8 s    | 约 55.0 s    | 0.327           |
| WhisperX GPU int8_float16 | 229.795 s | 约 21.1 s    | 约 26.7 s    | 0.116           |

从点击生成开始，按约 500 ms 轮询观测，含进程启动、加载、解码、识别/对齐、标点、持久化和观测延迟。两项使用不同歌曲，在同一运行中先后执行，不作为严格的同样本 CPU/GPU 对比。

CPU 任务首次“生成前缀已覆盖当前播放位置”时，媒体已到约 27.7 秒；相邻采样均确认播放领先处理的区间累计约 31.8 秒，包含开头等待及短暂再次落后。GPU 首次覆盖约在媒体 21.4 秒，确认落后区间约 20.0 秒。覆盖状态变化之间的采样区间单列，不假定整个间隔均已覆盖。第三曲无新任务，不计作识别覆盖。

本机这两次任务总处理速度快于输入时长，普通播放可以并行继续；首次收听仍有未覆盖区间。从开头伴读时可先生成一段再播放。这个结论只谈处理前缀，文字正确性、发音边界及演播质量仍需代表性样本和人工参考。

CPU 任务处理问题标记为 0，GPU 为 3，不作为人工错误率。CloudMusic 没有可用内嵌歌词，唯一 22 字节 LRC 是“暂无歌词”占位，参考候选为 0，没有计算歌曲 CER 或将模型输出充当参考。

## 窗口与测量边界

首轮播放期间调用 hide/show，间隔 30 秒，媒体时间继续推进。应用设置 `backgroundThrottling: false`，DOM `visibilityState` 在本轮始终为 visible，没有用它推断窗口实际可见状态。后续入口增加 `BrowserWindow.isVisible()` 断言，并通过独立原生窗口采样 smoke。相关行为见 [Electron WebPreferences](https://www.electronjs.org/docs/latest/api/structures/web-preferences)。

约 9 分 23 秒自然连播是短期基线。实际 MP3/M4A/M4B、较长听书单集、多小时资源稳定性、人工质量和干净设备安装仍按原计划保留。
